CloudFront Functions and Lambda@Edge run code at CloudFront events so a request or response can be changed during delivery. A trigger is an association between a function and an event on a cache behavior, the rule for a set of URL paths. Event placement decides whether the function also runs for cached content.

### How it works

1. On the normal request path, the viewer request event happens before cache lookup. Use this point to normalize, or make consistent, request values that form a cache key, the identifier for stored content.
2. A cache hit skips origin events. When CloudFront forwards to the origin, the origin request event can change the request or call an external service. An authorization token is information sent by a client to prove access; Lambda@Edge can inspect it or call an identity service to confirm credentials.
3. An origin response event runs after the origin replies and before caching. It also runs for origin errors, but not for a response generated by an origin-request function.
4. The viewer response event runs before delivery for normal cached and origin responses. Lambda@Edge skips it for origin responses of `400` or higher, custom error pages, viewer-request-generated responses and automatic HTTP-to-HTTPS redirects. Viewer request is also skipped for custom error-page fetches and automatic redirects.
5. To deploy Lambda@Edge, create the function in `us-east-1`, publish a numbered version and associate it with the behavior event. AWS replicates it globally; it processes events after the distribution deploys.

The following table compares HTTP request and response functions.

| Capability | CloudFront Functions | Lambda@Edge |
|---|---|---|
| Events | Viewer request and viewer response | Viewer and origin request and response |
| Runtime | JavaScript | Node.js or Python |
| Execution duration | Submillisecond | Up to 30 seconds |
| Network, file system, request body | No access | Access supported |

Since November 2025, CloudFront also supports Connection Functions for mutual TLS (mTLS), where client and server both prove identity with certificates. These functions run during the TLS handshake to allow or deny a connection using custom certificate checks. They cannot modify HTTP requests or responses.

To expose the request body, the data sent with a request, to Lambda@Edge, select `Include Body`. CloudFront exposes it as base64, a text encoding for binary data, and truncates it at 40 KB for viewer request or 1 MB for origin request. Reading without replacement still forwards the full original body to the origin.

### Exam cues

- If the question says lightweight redirects or consistent cache keys, think CloudFront Functions at viewer request, because these are supported uses before cache lookup.
- If the question says call an external service only before origin forwarding, think Lambda@Edge origin request, because CloudFront Functions has no network access and origin request skips hits.
- If the question says consult an identity service before serving cached private content, think Lambda@Edge viewer request, because origin-request authorization never sees cache hits.

### Remember

- Lambda@Edge uses `us-east-1` and a numbered version, not `$LATEST` or an alias.
- An origin-request function can run twice during origin-group failover.
- Lambda@Edge viewer-response functions cannot change the HTTP status code.

> **Trap:** Origin-request authentication protects origin forwarding. It does not run when CloudFront serves a cache hit.
