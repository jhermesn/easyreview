ALB metrics show trends in errors, connections, and response time. Access logs record individual requests so an operator can investigate which clients and targets were involved. Connection metadata carries the original client information through a load balancer.

### How it works

1. Compare the error metrics using the `Sum` statistic.

   | Signal | What it measures |
   |---|---|
   | `HTTPCode_ELB_5XX_Count` | 5XX responses generated by ALB |
   | `HTTPCode_Target_5XX_Count` | 5XX responses generated by targets |
   | `TargetConnectionErrorCount` | Failed ALB-to-target connections, excluding health check connections |
   | `TargetResponseTime` | Seconds until a target starts sending response headers after ALB sends the request |

2. Enable access logs and select an S3 bucket. The compressed logs include client addresses, paths, latencies, and responses. `target_status_code` is present only when ALB established a connection and the target responded.
3. For HTTP client addresses, use `X-Forwarded-For`, a request header containing address information. ALB defaults to `append`; `preserve` leaves the header unchanged and `remove` deletes it. Trust entries only when secured network systems added them.
4. For NLB TCP connection metadata, enable Proxy Protocol v2 only after the target can parse its binary header. NLB adds this header before TCP data and includes it in health check connections too.
5. For ALB logs, use an S3 bucket in the same Region with SSE-S3 and a bucket policy granting the log delivery principal `s3:PutObject` on the account-specific log path.
6. ALB idle timeout closes an inactive connection. Client keepalive limits the lifetime of a persistent HTTP connection; lowering it can help clients reconnect after an Amazon Application Recovery Controller zonal shift, but does not change existing connections.

### Exam cues

- If the question says 5XX responses rose after deployment, think compare ALB and target counters, because they distinguish response origin.
- If the question says investigate one client's failed request, think S3 access logs, because they contain request details.
- If the question says recover client addresses for HTTP behind ALB, think `X-Forwarded-For`, because it carries addresses through the proxy.
- If the question says a TCP backend needs source and destination metadata, think Proxy Protocol v2, because its binary header carries connection information.
- If ALB log delivery to S3 fails, check the bucket Region, encryption and log delivery policy.

### Remember

- ALB access logs are disabled by default.
- ALB and target 5XX counters exclude each other's responses.
- `TargetResponseTime` is measured in seconds.
- Default `X-Forwarded-For` mode: `append`.
- Proxy Protocol v2 requires a compatible parser on the target.
- ALB idle timeout defaults to 60 seconds; HTTP client keepalive defaults to 3600 seconds.

> **Trap:** An ALB-generated 5XX identifies who produced the response. A failed connection to a target can still be involved; inspect connection metrics and request logs.
